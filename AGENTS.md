# AGENTS.md — инструкция для агентов и разработчиков

Проект: парсер Ozon с фокусом на **китайских продавцов** и мини-CRM вокруг них.
Платформа: Python 3, браузерная автоматизация (Camoufox или Chrome), SQLite.

Прочитай этот файл целиком перед первой правкой — здесь собрано то, на что
уже потрачены часы отладки. Ниже отдельно отмечено, что проверено фактом, а
что осталось предположением.

---

## 1. Как быстро поднять и проверить

```bash
cd <репозиторий>
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # один раз

# Собрать китайских продавцов в базу (ссылка — раздел Ozon Global)
.venv/bin/python run_harvest.py harvest --pages 10

# Посмотреть, что в базе
.venv/bin/python run_harvest.py list --limit 30
.venv/bin/python run_harvest.py stats

# Дашборд с паролем из .env
./start_dashboard.sh          # http://127.0.0.1:8000
```

Тесты (без сети, секунды):

```bash
PYTHONPATH=. .venv/bin/python test/test_chinese_filter.py     # 33 кейса классификатора
PYTHONPATH=. .venv/bin/python test/test_outreach.py           # 14 кейсов метрик и лимитов
PYTHONPATH=. .venv/bin/python test/test_harvest.py            # 22 кейса: пауза, кэш, инкремент
PYTHONPATH=. .venv/bin/python test/test_wb_harvest.py         # 14 кейсов WB: запрос, классификация, база
PYTHONPATH=. .venv/bin/python test/test_workers_runtime.py    # 7 кейсов: pid/стейт/стоп-файлы воркера
PYTHONPATH=. .venv/bin/python test/test_communication.py      # 27 кейсов: ответы, категории, списки, миграция
```

Важно: тесты надо запускать с `PYTHONPATH=.` из корня. Без этого `test_simple.py`
и `test_seller_parser_simple.py` падают с `ModuleNotFoundError: No module named 'src'` —
это особенность их запуска, а не поломка.

## 3. Проверенные факты об Ozon (не переоткрывай заново)

### 3.1. Определение китайского продавца

**Единственный абсолютный признак — 18-значный USCC из блока реквизитов
продавца.** Формат: `91/92/93` + 6 цифр кода региона + 10 символов.
Пример: `91330782MAEATRWE13`.

Блок реквизитов в модалке `/modal/shop-in-shop-info?seller_id=<id>` — это
`textBlock` с `textColor: tertiary`, где строки склеены через `<br>`:

```
китайский продавец — три строки:      российский — две:
  Yiwushisenyibaozhuangzhipinyouxiangongsi    ИП Дубовик Василий Николаевич
  yiwushi                                     319703100086469   (ОГРНИП)
  91330782MAEATRWE13  ← USCC
```

Провинция Китая выводится из самого кода: цифры 3-8 — код региона GB/T 2260,
первые две цифры — провинция. Сверено на шести продавцах с реальными адресами
(`330782` → Zhejiang/Иу, `320594` → Jiangsu/Сучжоу, `360111` → Jiangxi/Наньчан,
`350802` → Fujian/Лунъянь). Таблица — `USCC_PROVINCES` в `chinese_filter.py`.

### 3.2. Раздел «Товары из Китая»

```
URL:  /highlight/tovary-iz-kitaya-935133/
API:  /api/composer-api.bx/page/json/v2?url=<путь>&__rr=1
```
Пагинация `?page=N`, минимум до 100-й страницы, **8 товаров на страницу**.
Проверено: товары на страницах 1, 2, 3 и 50 китайские (11 из 11).

Подтверждение вторым способом — виджет доставки, поле `global_info`
(см. `src/crm/verify.py`). Второй уровень нужен, потому что USCC есть не у всех.

### 3.3. Ловушки, на которых уже спотыкались

1. **Грид рекомендаций.** На странице раздела есть два товарных грида.
   Настоящий листинг — тот, у которого `params` строго `"{}"`.
   У рекомендаций в params есть `"title":"Возможно, вам понравится"`, и в них
   лежат обычные российские товары. В рекомендательном гриде 30 позиций против
   8 — легко польститься на «побольше товаров» и получить «китайский раздел»
   со складом в Ленинградской области.

2. **`country` / `countryCode` / `countryId` в ответах — это страна
   ПОКУПАТЕЛЯ.** Всегда `Россия` / `RUS` / `1`, к продавцу отношения не имеет.

3. **`from_global=true` — не фильтр.** Проверено: поиск с ним и без дал
   идентичные списки. Это флаг контекста, он лишь прокидывается в ссылки.

4. **`webDelivery` в ответе карточки всегда `{}`.** Состояние виджета грузится
   отдельным POST, которому нужен `asyncData` из узла `layout`. Без него — 400.

5. **Кириллица в ответах экранирована как `\u0417...`.** Сначала раскодируй
   строку, потом ищи текстовые метки (`_decode_escapes` в `harvest.py`).
   Не используй `decode("unicode_escape")` — он трактует строку как Latin-1
   и вместе с экранировками съедает кириллицу.

6. **`"Со склада продавца"` — не признак Китая.** Так пишет и российский
   продавец («Со склада продавца, Московская»). Признак — сам регион.

7. **Латиница в названии — не признак Китая.** У турецких товаров склад
   `Istanbul`, у польских — `Lower Silesian`.

### 3.4. Wildberries — СЕЙЧАС НА ПАУЗЕ (флаг WB_ENABLED, по умолчанию выкл)

Статус на 26.09.2026 (решение владельца: работаем чисто с Ozon):

* Весь WB-код в проекте жив (`src/parsers/wb/`, `src/workers/wb_harvest.py`,
  тесты), но дашборд его прячет: `WB_ENABLED=0` — в UI нет переключателя и
  карточки WB, все запросы с `marketplace=wb` сервер отклоняет. Вернуть —
  `WB_ENABLED=1` в `.env` + перезапуск дашборда.
* Отдельная среда для опытов без дашборда: `python run_worker.py
  --marketplace wb --url "запрос" --pages 1` (свой стейт, своя база
  `data/sellers-wb.sqlite3`; см. также docs/ISOLATION_WB.md).
* Почему пауза: WB банит по IP до всякой маскировки (проверено: домашний
  IP во флаге, VM 403 на search, зарубежный VPN — мгновенный 403 даже в
  настоящем Chrome с куками). Плюс переехал эндпоинт реквизитов (404).
* Как оживить: чистый резидентный IP (перезагрузка роутера / мобильный
  интернет / прокси в WB_PROXY) → снифф актуального seller-info из трафика
  страницы → одна строка в endpoints.py → WB_ENABLED=1.

### 3.4.1. Wildberries — проверено вживую 26.09.2026 (не переоткрывай заново)

Сбор китайских поставщиков WB работает **без браузера** — но только через
`curl_cffi`. Ключевые факты:

1. **WB фильтрует по TLS-отпечатку.** Обычный `requests` получает 403 на
   `search.wb.ru` и `catalog.wb.ru` (пустое тело). `curl_cffi` с
   `impersonate="chrome"` проходит. Прокси — `WB_PROXY` в `.env`
   (пусто = с IP машины).
2. **Антибот-страница** («Подозрительная активность», челлендж от
   `captcha-support@rwb.ru`, код 498 на главной) вешается по IP и держится
   минуты. Пойманный IP надо либо выждать, либо сменить прокси.
3. **Версии эндпоинтов меняются часто**: карточка `card.wb.ru/cards/v2/detail`
   мертва (404), живая — `cards/v4/detail`; ответ сразу `{"products": [...]}`,
   без обёртки `data`. Поиск: `search.wb.ru/exactmatch/ru/common/{v}/search`,
   кандидаты v18/v13/v5. Все списки — в `src/parsers/wb/endpoints.py`:
   переезд API = добавить строку.
4. **`supplierId` лежит прямо в выдаче поиска** — отдельные запросы карточек
   для поиска продавца не нужны (главное отличие от Ozon, где продавца
   выцарапывают из виджетов карточки). Батч карточек (`nm=1;2;3` до ~100
   артикулов) всё равно оставлен в транспорте — пригодится для витрин.
5. **`dest=-1257786` (Москва)** — обязательный параметр, влияет на цены/остатки.
   Переопределяется `WB_DEST`.
6. **Реквизиты продавца (`seller-info`) — слабое место**: старый путь
   `static-basket-01.wbbasket.ru/vol0/data/seller-info-by-id-api/v2/{id}`
   отдаёт 404. Без него нет ИНН/адреса → нет классификации. Актуальный путь
   снять DevTools'ом с чистого IP; кандидаты уже перебираются
   (`WBHttpClient.supplier_info`).
7. **Классификация — тот же `chinese_filter`**: реквизиты WB (юрлицо, адрес,
   ИНН/ОГРН) склеиваются в формат модалки Ozon (`<br>`-строки), дальше работает
   общий классификатор. Российское юрлицо перебивает «китайские» маркеры:
   российский продавец китайских товаров — не китайский продавец.
8. **Рассылки на WB нет** — у витрины нет чата покупатель→продавец. Канал
   доставки для WB-продавцов не выбран (v1.9 пишет их в CRM со статусом `new`).

### 3.5. Два воркера на одной машине — как устроено

* Каждый маркетплейс — **отдельный OS-процесс** (`run_worker.py
  --marketplace ozon|wb`), а не поток: падение WB не задевает Ozon и дашборд.
* Общение с дашбордом — файлами (`src/workers/runtime.py`):
  `data/worker_<mp>.pid`, `data/worker_<mp>.state.json` (атомарная запись),
  `data/worker_<mp>.stop`. Стейт структурный — не парсить лог регэкспами.
* Супервайзер `dashboard/workers.py`: авто-рестарт упавшего (3 подряд —
  сдаться), новые строки лога воркера уходят в SSE с полем `marketplace`.
* **Конфликт браузера**: Ozon-воркер использует общий Camoufox/Chrome — перед
  его запуском дашборд запрещает legacy-задачи (сбор/ночной/рассылка), и
  наоборот. WB-воркер браузера не касается.
* Тесты воркера требуют `WORKER_DATA_DIR=<временная папка>` **до импорта**
  `src.workers.runtime` — иначе тесты трогают живые `data/`.
* Ручной запуск для отладки: `WORKER_DATA_DIR=/tmp/x python run_worker.py
  --marketplace wb --url "органайзер" --pages 1`.

### 3.6. Отзывы и ответы продавца — снято с живого API 26.09.2026 (не переоткрывай заново)

Источник «живости» продавца (`src/crm/review_sample.py`). Проверено пробниками на VM:

1. **В карточке товара отзывов НЕТ.** Есть только счётчик — виджет
   `webReviewProductScore` с полями `url` (путь страницы отзывов, например
   `product/slug-1687474411/reviews`, без ведущего слэша) и `reviewsCount`.
   Карточки без отзывов счётчик всё равно отдают — по `reviewsCount == 0`
   сэмпл не снимаем, экономим запрос.
2. **Список отзывов** — страница `/{url}` из пункта 1, виджет `webListReviews`,
   массив `reviews` (30 штук, самые свежие). Пагинация `?page=N` работает.
   У отзыва важны: `uuid`, `content.score` (звезды), `comments.totalCount`.
3. **`comments.list` в общей выдаче ВСЕГДА пуст** — тело комментариев приходит
   только по якорной ссылке `{страница отзывов}?ruuid={uuid отзыва}`, и только
   для якорного отзыва (30 остальных остаются пустыми). Запрос «вслепую» по
   `/product/{id}/reviews?ruuid=…` (без слага) может не сработать — строить
   якорь из пути счётчика/`sharing.url` (со слагом).
4. **Ответ продавца — это комментарий** в `comments.list`, опознаётся по
   автору: у магазина `author.clientOfficial.id` равен его seller_id (не
   `"0"`), `partnerType: 1`, имя и `brandUri`. У покупателя `id: "0"`.
   **Поле `isUserComment` НЕ различает их** — оно `False` у обоих (проверено
   на живых примерах: ответ OUYA01 и комментарий покупательницы).
5. **`totalCount > 0` ≠ ответ продавца**: в комментариях пишут и покупатели.
   Поэтому для честной статистики отзыв с комментариями надо якорить; отзывы
   сверх лимита якорей из сэмпла выпадают (`plan_sample`), а не засчитываются
   молчунами. Отзыв с `totalCount == 0` разрешён достоверным: ответ продавца —
   сам был бы комментарием.
6. Страница `/seller/{id}/reviews/` композером отдаёт только оболочку магазина
   (24 виджета, списка отзывов нет) — быстрым путём «все отзывы продавца сразу»
   не получилось; если понадобится, искать отдельный API, а не этот URL.

## 4. Исправленные баги (не верни их обратно)

### 4.1. Гонка на общей вкладке Chrome — причина ложных «китайцев»

`SeleniumManager` в режиме подключения к обычному Chrome открывает вкладку
на каждого воркера (`_open_own_tab`) и делает её активной перед каждой
операцией (`_focus_tab`). Без этого все воркеры работали в ОДНОЙ активной
вкладке: пока один ждал JSON продавца A, другой уводил вкладку на продавца B,
и первый читал чужие реквизиты.

Последствие было тяжёлым: одна китайская компания оказалась приписана пяти
разным витринам, включая «Яндекс Фабрику», а в поле компании попадал текст
интерфейса («Фото и видео покупателей», «Товар закончился»). Пользователь
проверял ссылку и видел российского ИП Маликова вместо китайского продавца.

`camoufox_manager.py` этой болезни не подвержен: там `context.new_page()` на
каждого воркера.

### 4.2. Классификатор судил по всему JSON

Раньше USCC, иероглифы и «Китай» искались по всему сырому JSON карточки. В нём
десятки служебных токенов и тексты отзывов, поэтому российский ИП с валидным
ИНН получал «китайский код» (нестрогая регулярка `\b[0-9A-Z]{18}\b` ловила
служебные токены) и метку «Китай». Теперь:

* USCC ищется строго по форме `9[123]\d{6}[0-9A-Z]{10}` и только в реквизитах;
* иероглифы и «Китай» — только в названии продавца;
* подтверждённая российская регистрация (ОГРН/ОГРНИП/ИНН) перебивается
  **только** строгим USCC.

Тесты: `test/test_chinese_filter.py`, кейсы с пометкой `INVERTED:` фиксируют
именно это поведение.

### 4.3. Данные удалялись после отправки в Telegram

`app_manager._delete_output_folder()` делал `rmtree` папки с результатами.
Отсюда пустые папки в `output/`.

### 4.4. Дашборд терял данные

Он держал результаты в памяти и обнулял кэш при запуске нового парса. Теперь
вкладка продавцов читает базу, а предыдущие результаты остаются на экране,
пока идёт новый обход.

## 5. Что осталось непроверенным

Честно помечаю, чтобы никто не принял это за факт:

* **Отправка сообщений не тестировалась**: нет залогиненного аккаунта и нет
  снятых селекторов чата (нужен `python run_outreach.py inspect`).
* **Турецкие и прочие «глобальные» продавцы** на USCC не проверялись — только
  на склад (Istanbul, Lower Silesian → не Китай).
* **Китайский раздел — курируемая витрина**, а не весь рынок. Продавцов вне
  витрины этот способ не найдёт.
* **Не проверено, сходятся ли по USCC продавцы из витрины и их реальные
  реквизиты.** Уточнено: **один USCC на несколько витрин — это норма**, а не
  признак путаницы. Подтверждено дважды: компания `Nanchangtuboshumaoyi`
  (`91360106MA7FP0LG42`) держит магазины `tuboshu` и `ct`, а компания
  `91360111MAC3F9Y20A` — `Rhapsody Home Shop` и `Vandefa`. Один продавец =
  одна витрина — неверное допущение, если строите отчётность.

## 5.3. Где живут данные (локально на Mac)

База — одна SQLite: `data/sellers.sqlite3`, режим журнала **WAL**
(`synchronous=NORMAL`, `busy_timeout=30s`). WAL здесь не для красоты: дашборд
читает базу, пока харвестер пишет, и в обычном режиме журнала чтение падало бы
с «database is locked».

Резервные копии — `python tools/backup_db.py`:

| Что | Куда | Зачем |
|---|---|---|
| Снимок базы | `data/backups/sellers-<штамп>.sqlite3` | восстановление, хранится 20 последних |
| Выгрузка CSV | `backups/sellers.csv` | читаемая копия, попадает в git |

Снимок делается через `sqlite3.Connection.backup()`, а не копированием файла:
копирование может поймать базу в середине транзакции и дать битый снимок.

`--push` дополнительно коммитит CSV в приватный репозиторий — это офсайт-копия
вне машины, и для неё не нужно ничего настраивать. Сам файл базы в git не
кладём: бинарный и меняется целиком.

Восстановление: `python tools/backup_db.py --restore data/backups/<файл>`.
Текущая база при этом сохраняется как `.sqlite3.before-restore`.

Там же, в `data/`, лежат `harvest_settings.json` (сохраняемые ссылки и
параметры обычного и ночного сборов — раздельные секции) и стейт-файлы
ночного сбора/воркеров. Деплой `data/` не трогает: настройки машинно-локальные.

## 5.4. Чат с продавцом — снято с живой страницы 25.09.2026

Схема отправки, проверенная в залогиненной сессии:

1. открыть `https://www.ozon.ru/seller/{seller_id}/` (страница магазина);
2. нажать кнопку с текстом **«Написать»** — она там ровно одна;
3. дождаться `<textarea>` — на странице чата он единственный;
4. ввести текст и нажать **последнюю кнопку в блоке с полем ввода**.

Готовые селекторы лежат в `outreach_data/selectors.json`:

| Поле | Селектор |
|---|---|
| `login_marker` | `css|a[href="/my/main"]` |
| `chat_button` | `text=Написать` |
| `message_input` | `xpath|//textarea` |
| `send_button` | `xpath|//textarea/ancestor::div[2]//button[last()]` |

**Почему селекторы структурные, а не по классам.** Ozon обфусцирует имена
классов и добавляет к ним хеш сборки: `om_17text--SRiT5`, `b25_9_1-a`. Хеш
меняется между сборками, поэтому привязка к классам сломается на первом же
обновлении фронтенда. Селекторы выше опираются на тег и структуру.

**Кнопка отправки опознаётся по поведению.** У неё нет ни текста, ни
`aria-label`, ни `data-testid`. Зато она **заблокирована, пока поле пустое**, и
разблокируется после ввода — это проверено. Поэтому после нажатия мы считаем
признаком успеха то, что поле снова пустое: Ozon не отдаёт квитанцию об
отправке, и «нажали кнопку» — не доказательство.

**Прямая ссылка на чат не работает без подписи.** Вид
`/my/chat/?channel=cs&context=seller_storefront&url_sign=<токен>&user_id=<seller_id>`
требует `url_sign`, который генерируется на клиенте при нажатии. Без него Ozon
срезает параметры и открывает главную. Поэтому воспроизводим нажатие, а не
переходим по ссылке.

**Товар больше не нужен.** Чат открывается по странице магазина, то есть
достаточно `seller_id`. Раньше требовалась ссылка на товар — из-за этого в
очередь попадало 251 продавца вместо 565.

**Требуется вход в Ozon.** У незалогиненных кнопки «Написать» нет. Причём
сессия нужна в **профиле парсера** (`~/.ozon_parser_chrome`), а не в вашем
обычном браузере: отправитель запускает Chrome со своим профилем. При первом
запуске откроется окно — войдите в аккаунт один раз, дальше сессия сохранится.

### Почему не serverless

Парсинг требует настоящего браузера (Camoufox — Firefox со спуффингом
отпечатка, ~200 МБ), работающего минутами. У Cloud Functions лимиты по времени
и нет браузера с постоянным диском, а с датацентрового IP витрина ещё и под
челленджем. Serverless годится для **раздачи дашборда** (статика в Object
Storage + функция для API), но сбору нужна машина с рабочим IP.

### 5.5. Результаты коммуникации — как устроено хранение (26.09.2026)

Подготовка к массовой рассылке. Требование: **ни один ответ продавца не
теряется**. Правило: парсер и очередь не переписывались, всё — надстройка
над `data/sellers.sqlite3`.

**Где что лежит:**

* Полная история переписки — таблица `messages`. Входящие от продавца —
  строки `result='received'`, текст хранится **целиком** (никаких обрезок и
  служебных префиксов), `sent_at` — время получения, `category` — категория
  ответа. Старые записи с префиксом «[входящее …]» чистит
  `run_crm.py recategorize`.
* Текущее состояние продавца — колонки `sellers`: `reply_category`
  (категория последнего ответа), `reply_at` (когда ответил),
  `handed_to_manager_at` (передан менеджеру), плюс прежние `status`,
  `sent_at`, `message_sent`, `stage`.

**Категории ответов** (ключи в базе → русские метки в отчётах, см.
`REPLY_CATEGORY_LABELS` в store.py): `positive`, `negative`, `neutral`,
`interested`, `needs_info`, `other`. «НЕ ОТВЕТИЛ» в базе не хранится — это
производное состояние (писали, входящих нет), его выводят отчёты. Ставит
категорию `src/crm/classify.py` (ключевые слова, порядок правил важен:
негатив раньше позитива), человек может поправить в карточке дашборда.
Заинтересованные = `positive` + `interested` + `needs_info`
(`INTERESTED_CATEGORIES`).

**Передача менеджеру** — `run_crm.py handover` или кнопка в карточке:
ставит `handed_to_manager_at` и стадию «переговоры» (если была пустой).
Никаких копий продавца не создаётся — фильтр по колонке.

**Откуда полный текст (проверено на живом чате 26.09.2026):** композер-API
страницы чата отдаёт только оболочку аккаунта — сами сообщения Ozon гоняет
по WebSocket, и прямая ссылка не работает без url_sign (см. 5.4). Работает
путь отправщика: страница магазина → «Написать» → открытый чат. В разметке
чата у каждого сообщения есть атрибут `is-mine` («mine» — наше, пустой —
собеседник или система Ozon), время — span с чч:мм. Служебные сообщения
«Ассистент Ozon…» приходят с пустым is-mine и обязаны фильтроваться
(`SYSTEM_REPLY_MARKERS` в inbox.py), иначе подсказка системы сохранится как
ответ продавца. Открытие чата отмечает сообщения прочитанными в Ozon —
другого способа достать полный текст нет. Проверка: backfill по YM Store
снял ровно тот же текст, что лежал в базе превью — ничего не было обрезано.

**Отчёты** — `run_crm.py`: `report` (сводка), `interested`,
`no-reply`, `replies --category`, `seller <имя|id>` (карточка),
`handover`, `recategorize`, `backfill [продавец]` (дотянуть полный текст
ответа из живого чата для тех, кто ответил до апгрейда). Те же списки в
дашборде: фильтр «категория ответа» над таблицей, чипы категорий в строках,
воронка на «Обзоре» теперь считает «Написали/Ответили/Не ответили» по
журналу `messages`, а не по ручным статусам.

### Путь в облако, когда понадобится доступ отовсюду

1. *Сейчас:* база на Mac, офсайт-копия в репозитории. Бесплатно.
2. *Доступ извне при включённом Mac:* SSH-туннель, как в `tools/vm_tunnel.sh`.
3. *Нужна автономность:* поднять VM, залить снимок базы, служба уже настроена
   (`tools/deploy_vm.sh`). Не забыть уменьшить конфигурацию — сейчас там 2 ядра
   с гарантией 100% vCPU и SSD, это самое дорогое сочетание.
4. *Настоящая облачная база (если появится несколько пользователей):* Managed
   PostgreSQL в Yandex Cloud. Для одного пользователя с тысячами строк SQLite
   избыточен заменять — выгоды нет, а денег и мороки прибавится.

## 5.1. Работа с VM в Yandex Cloud — проверена фактически

Ранее здесь стояло «не проверено». Теперь проверено прогоном на живой VM
(`ubuntu@130.193.51.137`, код в `/opt/parser_ozon`, служба
`ozon-dashboard.service`).

**Важный факт, опровергающий прежнюю документацию:** с датацентрового IP
главная Ozon **отдаёт антибот-челлендж**, и Camoufox его не проходит (страница
~7 КБ). Но внутренний API по прямому переходу отдаётся нормально. Поэтому:

* `src/crm/harvest.py` определяет челлендж (по размеру страницы и маркерам) и
  переключается с быстрого `fetch` на прямые запросы к API через навигацию;
* результат проверки на VM: 8 товаров → 7 продавцов → **5 подтверждены по
  USCC** за ~26 секунд, 23 запроса.

Развёртывание: `bash tools/deploy_vm.sh` (rsync + зависимости + перезапуск
службы). Скрипт не трогает `config.txt`, базу `data/` и venv на VM.

Как устроена VM: Xvfb на `:99` поднимается обёрткой `vm-start.sh`, служба
слушает `0.0.0.0:8000`. Пароль дашборда — в `/opt/parser_ozon/.env` (права 600).

## 5.2. Что осталось непроверенным про VM

* Только один прогон, одна страница. Глубокий обход (десятки страниц) с VM не
  гонялся: неизвестно, начнёт ли Ozon притормаживать сессию и как быстро.
* Не проверено, сколько времени Camoufox живёт без утечек памяти при
  длительном обходе.

## 6. Правила работы с этим репозиторием

* **Не ослабляй проверки ради зелёных тестов.** Если легаси-кейс падает из-за
  смены контракта — поменяй ожидание осознанно и напиши почему, как сделано в
  `INVERTED:`-кейсах, а не удаляй проверку.
* **Темп запросов к Ozon сдерживай.** На ~150 запросах подряд сессия начинает
  виснуть (проверено). В харвестере пауза задаётся `--delay`.
* **Не добавляй обход детекции.** Маскировка в `selenium_manager._apply_stealth`
  существовала до этой работы; расширять её (подмена отпечатков, мультиаккаунт
  для обхода лимитов) не нужно.
* **Секреты только в `.env`** (он в `.gitignore`). Пароль дашборда —
  `OZON_DASHBOARD_PASSWORD`.
* Комментарии — по-русски, как во всём проекте. Объясняй «почему», а не «что».
