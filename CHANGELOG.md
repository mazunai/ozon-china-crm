# CHANGELOG парсера Ozon

## v1.19.0 — мультиаккаунт: 3–4 менеджера на одной машине (2026-10-02)

Решение владельца от 02.10.2026: правило «мультиаккаунт не строим» из AGENTS.md
§6 пересмотрено. Аккаунт — отдельная личность со своими лимитами, НЕ запасная
корзина: автопереключения на другой аккаунт при ограничении по-прежнему нет,
подмены отпечатков нет. Правила — в AGENTS.md §5.10.

- **Реестр аккаунтов** (`src/outreach/accounts.py`, `outreach_data/accounts.json`):
  id, подпись, профиль Chrome, порт отладки + необязательные переопределения
  лимитов (daily_cap, интервал, окно). `main` — исторические профиль и порт,
  существующая сессия работает без переделок.
- **CLI**: `accounts` (список/--add/--remove), `login --account`, `check
  --account`, `send --account`; чтение ответов `run_crm.py backfill --account`.
  Один аккаунт = один процесс ОС: свой Chrome (профиль = свои cookie сессии,
  свой порт), очередь в базе размечает продавцов атомарно (`BEGIN IMMEDIATE`),
  дублей между аккаунтами не бывает.
- **Лимит по аккаунту**: `sent_today`/`sent_since` считают по
  `sender_account_id` — у каждого менеджера свой дневной лимит и своё окно
  (переопределения в accounts.json поверх общих настроек sender.json).
- **Стоп-краны двух уровней**: глобальный `outreach_data/STOP` останавливает
  все аккаунты (дашборд/автономный режим/оператор — без изменений); аккаунтный
  `STOP_<id>` ставит Risk Control при ограничении — один менеджер под лимитом
  платформы не останавливает остальных. `resume` (и сторож по сроку платформы)
  снимает краны всех аккаунтов.
- **Ответы не теряются**: читалка входящих и фоллоу-апы умеют работать по
  конкретному аккаунту; фоллоу-ап пишется только СВОИМ контактам (main — всем,
  кроме контактов других аккаунтов), иначе продавцу пишет незнакомец.
- **Исправлен баг Risk Control**: в `trigger_risk` переменная `until_at`
  использовалась до присваивания — при первом же ограничении платформы
  стоп-кран не записывался (UnboundLocalError).
- `tools/start_senders.sh` — запуск всех аккаунтов одной командой с pid-файлами
  и логами `logs/sender_<id>.log`.
- **Панель «Аккаунты менеджеров» в дашборде** (вкладка «Рассылка»): таблица
  аккаунтов с портами, статусом сессии (авторизован / сессия стухла / жду
  вход), временем проверки и счётчиком отправок дня. Кнопка «Войти» открывает
  Chrome аккаунта в фоне (на VM окно видно через noVNC — вводить логин/пароль
  там), «Проверить» подтверждает сессию. Статусы в
  `data/accounts_status.json`, обновление в UI по SSE; сторож раз в 15 минут
  сам проверяет по одному не-main аккаунту, стухшая сессия уходит в Telegram.
  API: `GET /api/accounts`, `POST /api/accounts/login`, `POST /api/accounts/check`.
- Тесты: `test/test_accounts.py` — 11 кейсов (реестр, порты, лимиты по
  аккаунту, стоп-краны, фоллоу-ап по своим контактам); в
  `test_dashboard_http.py` +11 кейсов API аккаунтов. Тест срока лимита в
  test_autonomous переведён на «завтрашнюю» дату — фиксированное «2 октября»
  ломалось на следующий день (проверено 02.10.2026).

## v1.18.0 — сторож сессии, фоллоу-апы, горячие лиды, ежедневные задания (2026-10-01)

- **Сторож сессии и Chrome** (`WATCHDOG` в дашборде): раз в 15 минут проверяет
  живость сессии Ozon (в свободное от рассылки окно, через общий замок
  браузера). Слетевшая сессия — одно уведомление в Telegram с инструкцией,
  пометка в UI; если рассылка шла — она останавливается сама (продавцы не
  сжигаются ошибками «нет чата»). Упавший Chrome перезапусается службой
  `ozon-chrome` с сохранением профиля. Отключение: OZON_SESSION_WATCHDOG=0.
- **Предохранитель «мёртвой сессии» в sender**: 3 продавца подряд без чата —
  прогон останавливается с внятной причиной вместо перевода всей очереди в
  «пропущен».
- **Фоллоу-апы** (`src/outreach/followup.py`): вежливое второе касание тем,
  кто «написан и молчит > N дней» (по умолчанию 14). Отбор строго по правилам:
  статус ровно `sent`, ни одного ответа за всю историю, фоллоу-ап уже не
  отправлялся (`campaign_id='followup'`), ответившим/отказавшимся/opt-out —
  никогда. Текст — `outreach_data/followup.txt` (вне основной ротации),
  выключено по умолчанию, лимит за проход и паузы настраиваются; кнопка
  «Фоллоу-ап сейчас» в дашборде и автоматический проход перед раундами
  автономного режима. Ограничение платформы останавливает фоллоу-ап.
- **Горячие лиди — мгновенно**: ответы категории
  interested/positive/needs_info/negotiation приходят в Telegram отдельным
  «🔥 ГОРЯЧИЙ ЛИД»; отказы и нейтральные — только в журнал и статистику.
  Плюс алерт при падении отправки с причиной.
- **Ежедневные задания** (`DAILY_JOBS`): ночной пересчёт Lead Score (03:30) и
  утренний отчёт в Telegram (09:00, время — OZON_REPORT_TIME): отправлено за
  24ч, ответы/горячие, очередь, стадия переговоров/сделок, статус сессии,
  инциденты, автономный режим. Отключение: OZON_DAILY_JOBS=0.
- UI: поля фоллоу-апа в карточке «Запуск», статус сессии сторожа, статус
  фоллоу-апа в страховочном опросе.
- Тесты: `test/test_followup.py` — 7 кейсов (отбор кандидатов, порядок,
  конфиг, защита текста, предпросмотр, статистика горячих). Полный набор
  зелёный.

## v1.17.0 — Lead Intelligence: скоринг, мультиаккаунт, воронка, эксперименты (2026-10-01)

Раздел 11 ТЗ. Принцип: расширяем существующее, не дублируем. Полное описание —
`docs/LEAD_INTELLIGENCE.md`.

- **Мультиаккаунт и глобальная защита от дублей (§11.5)**: справочник
  `sender_accounts`; в журнал сообщений добавлены `sender_account_id`,
  `campaign_id`, `experiment_id`, `platform_message_id` (миграция на живой
  базе). Перед КАЖДОЙ отправкой проверяется общая история продавца
  (`prior_contact`) — не только история текущего аккаунта: второй аккаунт
  менеджера не напишет тому, кому уже писал первый, даже если статус продавца
  сбрасывали вручную. Политика повторов в настройках: `never` (по умолчанию)
  или `after_days` (фоллоу-ап не раньше N дней). Отказ от рассылки глобален
  для всех аккаунтов.
- **Lead Scoring (§11.2)**: Commercial (0–100: заказы/отзывы/срок/рейтинг в
  лог-шкале базового score + ассортимент + целевые ниши, множители полноты и
  свежести данных) и Engagement (0–100 от фактов коммуникаций, с уровнем
  уверенности — «мало данных» честно помечается). Итог 0.7/0.3. Каждая оценка
  объяснима словами (`score_lead` → reasons).
- **Градация A/B/C/D/U (§11.3)**: пороги в `outreach_data/lead_config.json`;
  U — нет подтверждения китайского происхождения; ручная смена с причиной
  (`POST /api/seller/grade`), авто-пересчёт её не затирает.
- **Воронка (§11.7)**: журнал `lead_events` (Imported→…→Deal/Lost/Opt-out);
  события пишут существующие действия; **автоматический путь в Deal
  запрещён** — только оператор; причины потерь в reason; панель считает
  достижимость кумулятивно.
- **Эксперименты (§11.4)**: создание с критериями и вариантами (версии в
  `experiment_versions`), детерминированное назначение по хэшу
  (воспроизводимо), текст варианта главнее ротации при отправке, отчёт с
  baseline групп (score/заказы/рейтинг) и честной уверенностью («мало
  данных» < 30 отправок).
- **Панель (§11.9)**: страница `/leads` + `GET /api/analytics`,
  `GET /api/leads/top`, `POST /api/leads/recompute`,
  `POST /api/seller/next-task` — всё SQL-агрегатами по фактам.
- Тесты: `test/test_leads.py` — 16 кейсов (скоринг и объяснения, полнота
  данных, уверенность, градации, воронка, запрет авто-Deal, мультиаккаунт,
  политика повторов, миграция старой базы, детерминизм экспериментов).

## v1.16.0 — автономная обработка очереди + Risk Control (2026-10-01)

Задача «устойчивая автономная обработка базы»: аудит → минимальные изменения
в существующих модулях → тесты. Полное описание и карта архитектуры —
`docs/AUTONOMOUS_MODE.md`.

- **Автономный режим**: супервизор `AUTONOMOUS` в дашборде гоняет раунды
  обычной отправки (`SEND.start()` со всеми проверками и замками) без
  оператора: пауза 60 мин после пустой очереди, 20 мин после раунда.
  Состояние — `data/autonomous_state.json` (атомарная запись), единственность —
  pid-лок `data/autonomous.lock`. **Перезапуск дашборда не сбивает режим**:
  при старте сервер сам продолжает его (как ночной сбор), зависшие «sending»
  возвращает в очередь. Управление: `POST /api/autonomous/start|stop|resume`,
  `GET /api/autonomous`, CLI `run_autonomous.py status|resume`.
- **Risk Control** (`src/crm/risk.py`): скан страниц Ozon на маркеры
  ограничения (Antibot-челлендж, «подозрительная активность», «доступ
  ограничен», captcha; дополняются `outreach_data/risk_markers.json`) на трёх
  рубежах — проверка входа, переподключение вкладки, каждая страница продавца
  перед печатью текста. При попадании: мгновенная остановка прогона, стоп-кран
  `outreach_data/STOP`, инцидент в новой таблице `risk_incidents`, отдельный
  Telegram-алерт. **Автопродолжения нет** — и другого аккаунта/профиля/
  отпечатка в системе не существует; снимает паузу только оператор
  (`/resume`), закрывая инцидент.
- **Backoff и предохранитель**: серия технических сбоев удваивает паузу
  (5→60 мин, `backoff_base/backoff_max_minutes`), после
  `max_consecutive_failures` (5) раунд останавливается с «нужен человек».
  Это пауза при аварии, а не обход ограничений.
- **Атомарный claim_next**: захват продавца — `BEGIN IMMEDIATE` до чтения;
  раньше SELECT и UPDATE были вне транзакции, и два параллельных отправщика
  могли получить одну строку (двойная отправка). Регрессионный тест: 8
  потоков × 20 продавцов без дублей.
- **Приоритеты очереди**: колонка `sellers.priority` (миграция на живой базе),
  порядок выборки `priority DESC → score DESC` (order_fresh поднимает свежие
  метрики). Формула скоринга не менялась. Задать: `POST /api/seller/priority`.
- **Telegram-команды** (`src/notify/tgbot.py`, stdlib long polling без
  aiogram): `/status`, `/auto_start`, `/auto_stop`, `/resume`, `/help` —
  только для своего chat_id. Легаси `bot.py` параллельно не запускать.
- **Починен mark_skipped**: `SellerStore.mark_skipped` принимал один аргумент,
  а sender вызывал с двумя — каждое «личка закрыта» роняло весь прогон
  TypeError'ом; причина теперь пишется в last_error.
- Тесты: `test/test_autonomous.py` — 16 кейсов (атомарность под потоками,
  приоритеты, order_fresh, «перезапуск не отправляет повторно», жизненный
  цикл инцидента, риск-пауза и resume, backoff, лок, стейт, парсер команд).
  Все остальные наборы зелёные.

## v1.15.0 — пул текстов для рассылки (ротация) + A/B-ранжирование + вход в Ozon через noVNC (2026-09-30)

- **A/B-ранжирование текстов**: выбор идёт не только по «реже использовался», но и
  по отдаче. `store.template_performance()` считает по каждому тексту отправки и
  неотрицательные ответы (`result='received'`, категория не `negative`), а
  `TemplatePool.pick(performance=...)` ранжирует по сглаженной доле ответов
  (Лаплас: `(replies+1)/(sent+8)`), с полом исследования
  (`AB_MIN_EXPOSURE=5` — новый текст сначала набирает показы) и долей эксплорейшена
  (`AB_EXPLORE_SHARE=0.2`). Пока данных нет — работает прежняя честная ротация.
  `run_outreach.py templates` печатает таблицу рангов с пометкой `← лидер`.
- **30 китайских вариантов**: `outreach_data/templates/msg01.txt` … `msg30.txt`
  добавлены в ротацию (итого 31 текст с `main.txt`), каждый с opt-out-маркером
  `退订`; валидация `load()` знает китайские маркеры отказа (`退订`, `不再打扰`,
  `不想再收到`, `不感兴趣请`, `请勿再发`), поэтому такие тексты считаются
  пригодными, а не черновиками. На VM синхронизированы (пул 31/31).
- **Ротация текстов**: каталог `outreach_data/templates/` читается целиком (`TemplatePool`), каждому следующему продавцу уходит текст, который использовался реже остальных; один и тот же текст не уходит дважды подряд, даже если он отстал в раскладке. Раскладка живёт в журнале отправок — `messages.template_name` (миграция на живой базе, индекс строго после неё), перезапуск процесса ротацию не сбивает. Файл с меткой «ЗАМЕНИТЕ ЭТОТ ТЕКСТ» считается черновиком и в ротацию не попадает. CLI: `python run_outreach.py templates` (каталог + сколько раз что ушло), `preview` показывает тот же текст, который уйдёт следующим; `send`/`check`/дашборд работают с пулом, `--template` по-прежнему фиксирует один файл.
- **Вход в Ozon через браузер** (сессия слетает, когда Chrome на VM падает): на VM поднята служба `ozon-novnc.service` (websockify + noVNC, слушает только 127.0.0.1:6080); `tools/vm_tunnel.sh` теперь тянет три порта — 8001 (дашборд), 6080 (noVNC), 9222 (Chrome). Пароль VNC — `x11vnc -showrfbauth ~/.x11vnc.pass` на VM.
- **VPN на Mac глушит доступ к VM** (диагноз 30.09: ssh вис на banner exchange, порты VM молчали, `yc` падал по таймауту — виновник `hidemyname.vpn` в маршруте по умолчанию, utun6): `vm_tunnel.sh`, `vnc_tunnel.sh` и `deploy_vm.sh` теперь привязывают ssh к физическому интерфейсу (`-o BindInterface=en0`, переменная `OZON_VM_IFACE`). Подробно — в AGENTS.md, разделы 5.3–5.5.
- **Починен deploy_vm.sh**: путь к `deploy/vm_known_hosts` указывал на несуществующий `tools/` — любой вызов со strict-проверкой ключа хоста падал; проба интерфейса повторяется трижды (маршрут через VPN иногда рвётся и одиночная проверка ложно проваливалась).
- Тесты: +9 в test_outreach — ротация (разные тексты подряд, «наименее использованный», запрет повтора, черновики, естественная сортировка msg2<msg10), журнал шаблонов в базе, миграция старой базы, сценарий «8 текстов на 8 продавцов». Полный набор зелёный.


## v1.14.0 — закрытие находок глубокого аудита (39 находок) + типографика стат-строк (2026-09-27)

Аудит (4 аудита кода + 2 веб-исследования, независимое подтверждение high-находок) — полный отчёт в docs/DEEP_AUDIT.md.

- **P0 сервер**: логин отправлял ДВА ответа в одно соединение (root cause BrokenPipe-спама); утечка BROWSER_LOCK в Service.start (замок не освобождался при исключении — все браузерные задачи отказывали до рестарта); симметричные проверки NIGHT/SERVICE/WORKERS/HARVEST в стартах рассылки, воркера, legacy-парсера, /api/seller/reply, /api/inbox/check и InboxAuto; tg.send вынесен из защищаемого блока (падение уведомления возвращало 500 и провоцировало повторную отправку продавцу); валидация marketplace в Content-Disposition.
- **P0 данные**: add_sellers больше не затирает непустые метрики пустыми (21 подтверждённого с обнулённым uscc было в базе) и не понижает verified_by; find_seller_by_shop при дублях имён не угадывает (чёт в unmatched); inbox сохраняет превью ДО открытия чата (ответ больше не теряется при падении) и пишет каждый пузырь отдельной строкой журнала; delete_sellers чистит журналы в той же транзакции.
- **Бэкапы**: restore требует остановленный дашборд и снимает safety через Connection.backup (в WAL копия файла пуста/битая); проверка свободного места перед снимком; messages.csv в офсайт-выгрузке; parser-backup.service получил --push; launchd-таймер на Mac (deploy/mac/).
- **Инструменты**: deploy_vm.sh — полный pip install, exclude backups/, health по https, зафиксирован host key (deploy/vm_known_hosts); vm_tunnel.sh переписан на актуальную VM с pid-файлом; night_harvest — атомарная запись стейта, видит ретро-проход, докстринг без мёртвого таймера; локальный дашборд не открывает чат при ночном сборе.
- **Типографика**: строки-полоски (fb-bar) — счётчик одной строкой без переносов, заливка всегда видна, трек тоньше; убран дубликат ovRepliesAuto.
- **Root cause BrokenPipe найден аудитором**: `.fb-fill` был инлайн-элементом — width игнорировался, заливки не рисовались ни в одной полоске (display:block чинит все); harvest: запрещённый unicode_escape заменён на _decode_escapes; ротация лога воркера; чистка логов старше 30 дней.
- Тесты: +test_dashboard_http (11: 401, замок перебора, purge/delete защита, сироты), backfill-протокол в test_harvest_settings (33), грид-ловушка в test_harvest, test_verify (6), handover CLI (поймал реальный краш `_shop` на sqlite3.Row). Полный набор — 12 файлов, ~180 кейсов.

## v1.12.0 — живость продавца: отвечает ли он на отзывы (2026-09-26)

Новый сигнал для приоритизации рассылки: продавцы, которые отвечают покупателям, обычно и с оптовыми клиентами общаются живее. Данные честные — по сэмплу отзывов, снятому с живого API, без догадок об именах полей (разведка на VM, структуры зафиксированы в AGENTS.md §3.6).

- **Как снимается сэмпл**: во время сбора карточка товара и так открывается — из неё берётся счётчик `webReviewProductScore` (адрес страницы отзывов + `reviewsCount`), затем +1 запрос за страницей отзывов (30 свежих) и максимум 2 якорных запроса `?ruuid=<uuid>` за комментариями отзывов, у которых они есть. Ответ продавца — комментарий с `author.clientOfficial.id != "0"` (у магазина там его seller_id и `partnerType: 1`; у покупателя `id: "0"`; поле `isUserComment` не различает — проверено на живых примерах). Темп не страдает: запросы идут через общий клиент с адаптивной паузой, одному продавцу — один сэмпл за проход.
- **Честный учёт**: отзывы с непроверенными комментариями (сверх лимита якорей) из сэмпла выпадают, а не считаются молчунами. Отзыв без комментариев разрешён достоверно — ответ продавца сам был бы комментарием.
- **Схема**: у продавца колонки `reviews_seen`, `replies_seen` (копятся кумулятивно), `reviews_checked_at`; миграция аддитивная (ALTER TABLE), перед деплоем — снимок базы. Накопление — в `store.record_review_sample`, счётчики для «Обзора» — `store.vitality_counts`.
- **Уверенность** (`src/crm/vitality.py`, чистый модуль): сглаживание Лапласа `score = (replies + 1) / (seen + 2)`; при `seen < 3` — «мало данных». Пороги фильтра выражены и в SQL (для выборки), и в Python — тест сверяет их на сетке 40×40.
- **Дашборд**: колонка «Живость» с сортировкой по уверенности («отвечает 4/5» — числа из базы), фильтр «только отвечающие / только молчуны», блок «Живость продавцов» на «Обзоре» (проценты — только среди продавцов с достаточным сэмплом), колонка «Живость» в CSV.
- **Новые модули**: `src/crm/vitality.py` (уверенность и категории), `src/crm/review_sample.py` (сэмпл; сетевые сбои не роняют сбор). Тесты: `test/test_vitality.py` — 23 кейса (формула, границы, SQL-эквиваленты, опознание ответа, учёт сэмпла), существующие наборы зелёные (33+14+23+14+30+7).

- **Мобильная версия ведёт себя как приложение**: зум отключён (`user-scalable=no` + `touch-action: manipulation`), прокрутка без «резинки» (`overscroll-behavior: none`), нет подсветки тапов и выделения служебных элементов; в окне входа поле пароля 16 px — iOS не зумит при фокусе.

- Автозапуск по таймеру systemd сознательно не используется — сбор стартует только по кнопке.
