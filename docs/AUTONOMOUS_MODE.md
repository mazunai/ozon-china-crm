# Автономная обработка очереди (Autonomous Processing Mode)

Что система умеет сама, где останавливается и что в этот момент делает
оператор. Архитектурный аудит и план изменений — по задаче «устойчивая
автономная обработка базы продавцов» (30.09–01.10.2026).

## 1. Карта архитектуры (как было)

```
Данные:  SQLite data/sellers.sqlite3 (WAL, busy_timeout 30с, synchronous=NORMAL)
  sellers  — статусы, скоринг, приоритет, attempts, last_error
  messages — журнал каждого сообщения (текст, result, category, template_name)
  risk_incidents — журнал сигналов ограничения платформы (новое, v1.16)

Очередь:  SellerStore (src/crm/store.py)
  claim_next()        — атомарный захват: BEGIN IMMEDIATE → SELECT → UPDATE.
                        Порядок: priority DESC → score DESC (order_fresh: metrics_at DESC).
                        Только verified_by ∈ {uscc, warehouse}, только status='new'.
  release_stale(30м)  — зависшие «sending» возвращаются в очередь (аварийное восстановление)
  mark_sent / mark_failed(retryable) / mark_skipped / opt_out — переходы статусов
  sent_today()        — дневной лимит считается по messages.sent_at (не по sellers)
  template_usage / template_performance — ротация и A/B по журналу

Отправка: src/outreach/sender.py :: run_queue()
  ограничители: интервал+jitter, дневной лимит, рабочее окно 10:00–19:00,
  стоп-кран файлом outreach_data/STOP, dry_run по умолчанию, max_attempts
  браузер: свой профиль ~/.ozon_parser_chrome, вкладка переподключается сама,
  закрытая личка продавца → skipped (не сбой)
  Risk Control (v1.16): скан страниц на маркеры ограничения; при попадании —
  STOP-кран + инцидент в базу + полная остановка

Дашборд:  dashboard/server.py
  SEND  — раунд отправки в потоке дашборда (замок BROWSER_LOCK, preflight,
          симметричные проверки NIGHT/WORKERS/HARVEST/SERVICE)
  NIGHT — ночной сбор отдельным процессом (lock/state/stop-файлы)
  WORKERS, HARVEST, SERVICE — сбор и legacy-парсинг
  AUTONOMOUS (v1.16) — супервизор автономных раундов; раунд = обычный SEND.start()
  TG_POLLER (v1.16) — командный Telegram-бот (long polling, stdlib)

Сбор:     run_worker.py / tools/night_harvest.py → src/workers/ozon_harvest.py
```

## 2. Что добавлено (v1.16)

### 2.1. Атомарность очереди

`claim_next` раньше делал SELECT и UPDATE двумя операторами вне транзакции —
два параллельных отправщика получали одну строку, продавцу уходило два
сообщения. Теперь захват — `BEGIN IMMEDIATE` до чтения: выбор кандидата и
пометка «sending» происходят под одним write-локом SQLite. Покрыто
многопоточным тестом (8 потоков × 20 продавцов, ни одного дубля).

### 2.2. Приоритеты очереди

* колонка `sellers.priority` (INTEGER, по умолчанию 0), миграция на живой базе;
* порядок выборки: **priority DESC → score DESC** (order_fresh ставит выше
  свежие метрики); формула скоринга НЕ менялась;
* задать: `POST /api/seller/priority {seller_id, priority}` (−100..100 —
  соглашение, реализация принимает любое целое);
* прочие критерии уже были: подтверждённость (verified_by), отсутствие
  контактов (status='new'), свежесть метрик (order_fresh / scoring).

### 2.3. Backoff и предохранитель (технические сбои)

Серия сбоев (сеть, браузер, страница) удваивает техническую паузу:
5 → 10 → 20 … до 60 мин (`backoff_base_minutes`, `backoff_max_minutes` в
настройках отправки). После `max_consecutive_failures` (по умолчанию 5)
раунд останавливается с причиной «нужен человек». Это пауза, а не обход
ограничений: при маркерах ограничения платформы работает риск-стоп.

### 2.4. Risk Control (ограничения платформы)

Маркеры: «Antibot Challenge», «подозрительная активность», «доступ
ограничен», «подтвердите, что вы не робот», captcha и др.
(`src/crm/risk.py`). Дополняются файлом `outreach_data/risk_markers.json`.

Скан выполняется на трёх рубежах: проверка входа, переподключение вкладки,
каждая открытая страница продавца перед печатью текста.

При попадании маркера (`PlatformRestricted`):
1. отправка немедленно останавливается целиком;
2. ставится стоп-кран `outreach_data/STOP`;
3. инцидент пишется в `risk_incidents` (маркер, этап, продавец, время, снимок);
4. Telegram: отдельное уведомление «ОГРАНИЧЕНИЕ ПЛАТФОРМЫ»;
5. автопродолжения **нет**: ни другой аккаунт, ни профиль, ни отпечаток —
   таких механизмов в системе не существует;
6. оператор проверяет причину в браузере (noVNC/«Общий экран»), затем
   возобновляет: `/resume` в Telegram, `POST /api/autonomous/resume` или
   `python run_autonomous.py resume`. Это закрывает инцидент, снимает
   стоп-кран — следующий раунд уходит сам.

Временные ошибки обычной жизнью лечатся отдельно (2.3), повторами антифрод
не «пробивается»: закрытая личка — skipped без повторов; неоднозначная
отправка («не подтвердилась») — failed для человека, автоповтора нет,
потому что он мог бы задвоить сообщение.

### 2.5. Автономный режим

`src/outreach/autonomous.py` — супервизор раундов. Раунд — обычный
`SEND.start()` со всеми проверками и замками, ничего не дублируется.

* запуск: `POST /api/autonomous/start` (дашборд) — раунды идут сами, пауза
  после пустой очереди 60 мин, после обычного раунда 20 мин;
* штатная остановка: `POST /api/autonomous/stop` или `/auto_stop` — текущий
  продавец дописывается, новые не берутся;
* состояние: `data/autonomous_state.json` (атомарная запись) — счётчики
  раундов/отправок/ошибок переживают перезапуск;
* единственность: `data/autonomous.lock` (pid) — второй процесс не стартует;
* **переживает перезапуск дашборда**: при старте сервер видит `running=true`
  и мёртвый лок — продолжает режим сам (как ночной сбор). Аварийные «sending»
  возвращает в очередь `release_stale`;
* `python run_autonomous.py status` — состояние без браузера (удобно по SSH).

### 2.6. Telegram-команды

Бот на stdlib (`src/notify/tgbot.py`, long polling), стартует с дашбордом,
если заданы `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Слушает только
свой чат.

| Команда    | Действие |
|------------|----------|
| `/status`  | режим, раунды, отправлено/ошибок, очередь, инцидент |
| `/auto_start` | запустить автономную обработку |
| `/auto_stop`  | штатно остановить (дописав текущего) |
| `/resume`  | возобновить после ограничения платформы |
| `/help`    | список команд |

Не запускать `python bot.py` (легаси) одновременно: два getUpdates начнут
воровать апдейты.

## 3. Что уже было и переиспользовано

Стоп-кран файлом, dry_run, дневной лимит и рабочее окно, переподключение
вкладки, журнал messages с template_name, A/B-ранжирование, ночной сбор с

не переписывалось.

## 4. Известные ограничения (честно)

* Окно «сообщение ушло, но процесс умер до mark_sent» (< 1 сек между
  подтверждением в DOM и записью в базу) может привести к повторной отправке
  продавцу после аварийного перезапуска. Вероятность ничтожна, устранение
  потребовало бы транзакционных квитанций от Ozon, которых не существует.
* Приоритет задаётся через API (curl), кнопки в интерфейсе нет —
  сознательно, чтобы не раздувать UI.
* Риск-маркеры текстовые: если Ozon сменит формулировки на нераспознаваемые,
  сработают обычные предохранители (backoff, предохранитель по числу сбоев),
  но авто-стопа не будет — пополняйте `risk_markers.json`.
