## v0.3 — 25.09.2026 — Мини-CRM и исправление ложных «китайцев»

### Исправлено (критично)

* **Гонка на общей вкладке Chrome.** Все воркеры парсера работали в одной
  активной вкладке и перезаписывали друг другу страницу — из-за этого
  российским продавцам доставались реквизиты китайских фирм, а в поле компании
  попадал текст интерфейса. Каждый воркер получил свою вкладку.
  (`src/utils/selenium_manager.py`)
* **Ложные вердикты «Китай» у российских ИП.** Классификатор искал USCC по
  всему сырому JSON нестрогой регуляркой, которая ловила служебные токены Ozon.
  Теперь USCC строго по форме кода и только в блоке реквизитов продавца;
  иероглифы и «Китай» — только в названии продавца; российская регистрация
  перебивается только настоящим USCC. (`src/parsers/chinese_filter.py`)
* **Мусор в поле компании.** `seller_parser` выбирал «лучший textBlock»
  внутренним скорингом и брал текст интерфейса. Теперь ищет блок, у которого
  последняя строка — регистрационный номер.
  (`src/parsers/seller_parser.py`)
* **Дашборд терял данные при новом прогоне** — кэш обнулялся на старте парса.
  (`dashboard/server.py`)

### Добавлено

* Единое хранилище продавцов на SQLite с миграцией старой очереди и уровнями
  достоверности `uscc` / `warehouse` / `heuristic`. (`src/crm/store.py`)
* Харвестер раздела «Товары из Китая»: страницы → товары → продавцы → реквизиты
  → база, с защитой от грида рекомендаций. (`src/crm/harvest.py`)
* Подтверждение страны по складу продавца через виджет доставки.
  (`src/crm/verify.py`)
* CLI `run_harvest.py`: `harvest`, `list`, `show`, `stats`, `note`, `status`,
  `export`.
* Вкладка «Китайские продавцы» в дашборде: USCC, провинция, метрики, оценка,
  статус, заметка, ссылка на профиль.
* Авторизация дашборда (HTTP Basic, пароль в `.env`).
* Автосохранение продавцов в базу по завершении парса.

### Изменено

* `SellerInfo` дополнен полями `shop_name`, `registration_block`, `address`,
  `uscc`, `province`, `registration_kind`.
* `SellerClassification` дополнен полями `uscc`, `province`,
  `registration_kind`.
* Шесть кейсов в `test_chinese_filter.py` переведены в `INVERTED:` —
  фиксируют, что сигналы через служебный JSON больше не дают вердикт «Китай».

### Документация

* `AGENTS.md` — инструкция для агентов: карта проекта, проверенные факты,
  ловушки, исправленные баги, список непроверенного.
* `docs/PROJECT_MEMORY.md` — хронология решений и мотивировка.

## v0.4 — 25.09.2026 — Развёртывание на VM и адаптивный транспорт

### Проверено фактически (ранее было записано как непроверенное)

Сбор с VM в Yandex Cloud работает: 8 товаров → 7 продавцов → **5 подтверждены
по USCC** за ~26 секунд. Команда `bash tools/deploy_vm.sh` разворачивает код,
зависимости и перезапускает службу.

### Исправлено

* **`fetch` не работал на VM.** С датацентрового IP главная Ozon под
  антибот-челленджем, и запросы из её контекста блокируются. Из-за этого первый
  прогон на VM вернул 0 товаров. Транспорт стал адаптивным: харвестер
  определяет челлендж по размеру страницы и маркерам и переключается на прямые
  запросы к API — этот путь на VM работает. (`src/crm/harvest.py`)
* **Своя вкладка воркера не создавалась.** `switch_to.new_window("tab")`
  возвращал `None` вместо handle, и привязка молча не работала — то есть фикс
  гонки из v0.3 не действовал. Handle теперь берётся из
  `current_window_handle`. (`src/utils/selenium_manager.py`)
* **Подключение к Chrome падало**, если предыдущий запуск оставил браузер без
  открытых страниц (`unable to discover open pages`), и скрипт молча уходил в
  откат на автоматизированный Chrome. Добавлена проверка и создание вкладки.
* **Устаревший комментарий про Camoufox.** Написано, что он проходит проверку с
  датацентрового IP — это неверно. Исправлено с пояснением, как на самом деле
  работает обход. (`src/utils/camoufox_manager.py`)

### Добавлено

* `tools/deploy_vm.sh` — развёртывание на VM: rsync, зависимости, перезапуск
  службы, проверка ответа дашборда. Не трогает `config.txt`, базу и venv.
* Проверка origin перед запросами: с чужого домена `fetch` к Ozon блокируется
  как кросс-доменный, и это выглядело как «Ozon не отвечает».
* Понятные ошибки вместо пустых ответов: харвестер пишет причину, почему
  страница не получена.

### Известные ограничения

* Глубокий обход (десятки страниц) с VM не гонялся — неизвестно, начнёт ли Ozon
  притормаживать сессию.
* У двух витрин встретился один USCC (`Rhapsody Home Shop`, `Vandefa`) — нужно
  сверить профили вручную.

## v0.5 — 25.09.2026 — Локальная база «как в облаке», VM выключена

### Изменено

* **SQLite переведена в режим WAL** с `synchronous=NORMAL` и `busy_timeout=30s`.
  Дашборд читает базу, пока харвестер пишет — в обычном режиме журнала чтение
  падало бы с «database is locked». (`src/crm/store.py`)
* VM в Yandex Cloud **остановлена** (`yc compute instance stop`), разработка
  идёт на Mac. Данные на диске VM сохранены: при следующем старте будут на месте.

### Добавлено

* `tools/backup_db.py` — резервные копии: согласованный снимок через
  `sqlite3.Connection.backup()` в `data/backups/` с ротацией (20 последних),
  выгрузка в `backups/sellers.csv`, восстановление `--restore`, офсайт-копия
  `--push` в приватный репозиторий.

### Уточнено

* **Один USCC на несколько витрин — это норма.** Ранее было записано как
  подозрение на путаницу. Подтверждено дважды: `Nanchangtuboshumaoyi`
  (`91360106MA7FP0LG42`) держит магазины `tuboshu` и `ct`; компания
  `91360111MAC3F9Y20A` — `Rhapsody Home Shop` и `Vandefa`.

### Выяснено про serverless

Cloud Functions для парсинга не подходят: нужен настоящий браузер на минуты, у
функций лимиты по времени и нет постоянного диска, а с датацентрового IP витрина
под челленджем. Serverless годится для раздачи дашборда, но не для сбора.

### Замечено

* После прогона сбора на VM оставался висеть процесс Camoufox (493 МБ), хотя
  `close()` вызывается в `finally`. На 2 ГБ памяти такая утечка при длинном
  обходе опасна — стоит разобраться до уменьшения конфигурации VM.

## v0.6 — 25.09.2026 — Сбор из дашборда, проверка данных первого прогона

### Добавлено

* **Запуск сбора прямо из дашборда.** Блок «Собрать китайских продавцов»: ссылка
  на раздел (предзаполнена разделом «Товары из Китая»), число страниц, кнопки
  запуска и остановки, полоса прогресса. Работает в фоне, прогресс идёт в общий
  лог, по завершении таблица продавцов обновляется сама.
  Эндпоинты: `GET/POST /api/harvest`, `POST /api/harvest/stop`.
* Прогресс в харвестере структурный (`progress_cb`): три фазы с весами — сбор
  товаров, определение продавцов, проверка реквизитов.
* Команда `run_harvest.py reverify` — перепроверка продавцов, подтверждённых по
  складу: записывает регион как обоснование либо понижает до «не подтверждён».
* `SellerStore.set_verification_reason()` — смена уровня достоверности с причиной.

### Исправлено

* **Причины для уровня «склад» не сохранялись.** В базе было непонятно, по какому
  региону продавец признан китайским. Теперь регион пишется в `chinese_reasons`.
* **Запись в базу шла только в конце прогона.** Прогон на 50 страниц идёт около
  15 минут, и падение в середине обнуляло всю работу. Теперь запись порциями по
  25 продавцов — прогресс виден в дашборде сразу.

### Результат первого полного прогона

50 страниц раздела «Товары из Китая»: 350 товаров → 273 продавца, 946 запросов,
около 15 минут. В базе **268 подтверждённых** (242 по USCC, 26 по складу),
24 провинции, лидеры Zhejiang 64, Fujian 44, Guangdong 34.

### Выяснено

* **Подтверждение по складу работает на уровне товара, а не продавца.** У одного
  продавца разные товары могут отгружаться с разных складов. Перепроверка
  понизила 2 продавца из 26: у них виджет показал только «доставка из-за рубежа»
  без китайского склада. Для строгого требования «только Китай» это правильно,
  но проверять стоит 2–3 товара на продавца, а не один.

## v0.7 — 25.09.2026 — Российские юрлица убраны из подтверждённых

### Исправлено (критично)

* **Склад перебивал российскую регистрацию.** Уровень «подтверждён по складу»
  выставлялся без проверки юрлица, и в подтверждённые попадали российские
  компании: `ООО "АРАВИЯ"`, `ООО "СПЛ-ТЕХНИК РУС"`, `ООО "СИКЕЭР ЕВРАЗИЯ"`,
  `ООО "ПАНОРАМА ГРУП"` (три витрины), `ООО "ОРАНЖ ИСЛАНД"` (две),
  `ООО АКВАКОЙН`, `ООО Астра Норд`, `ООО РусЕвроСвет`, `ООО "АТМА ГРУП"`,
  `ИП Гиниятуллин`, `ИП Першин`. Логика была неверной: российское ООО может
  отгружать товар из Китая, но китайским продавцом от этого не становится.
  Теперь российская регистрация (ОГРН/ОГРНИП/ИНН) перебивает склад, и такой
  продавец получает уровень «не подтверждён». (`src/crm/harvest.py`)
* **Выгрузка CSV не фильтровала по подтверждению.** `tools/backup_db.py`
  складывал в файл все строки, включая неподтверждённые, и именно так в
  офсайт-копию попало российское `ООО КАРИ`. Теперь выгрузка содержит только
  подтверждённых; полный список — флаг `--all`. (`tools/backup_db.py`)
* **Неподтверждённые никак не помечались в интерфейсе.** Пометка была только у
  подтверждённых, поэтому при снятой галочке «только подтверждённые» отличить
  их было нельзя. Теперь у них красная метка «НЕ ПОДТВЕРЖДЁН».
  (`dashboard/web/index.html`)

### Добавлено

* `run_harvest.py purge` — удаление записей, не подтверждённых как китайские.
  Показывает список без `--yes`, требует явного подтверждения: операция
  необратима.
* `SellerStore.delete_sellers()`.
* `reverify` теперь сначала проверяет юрлицо, без обращений к сети: российская
  регистрация понижается сразу, склад для таких продавцов не проверяется.

### Результат чистки

Было 266 подтверждённых, стало **252** (242 по USCC + 10 по складу). Понижено
14 записей с российскими юрлицами. Из 10 оставшихся на складе у всех явная
китайская провинция.

## v0.8 — 25.09.2026 — Дашборд как CRM: вкладки, фильтры, карточка продавца

### Фаза 0: исправлено критичное

* **Кнопка «Остановить» у сбора была фиктивной.** Флаг отмены выставлялся и
  никем не читался — интерфейс писал «Останавливаю…», а обход шёл до конца.
  Теперь отмена проверяется в трёх циклах харвестера, работает за секунды,
  частичный результат сохраняется. Проверено: 30 страниц → стоп за 5 секунд.
* **Заметки терялись тремя способами.** Сохранялось только по уходу из поля;
  поле помечалось сохранённым до ответа сервера (провал не повторялся);
  перерисовка таблицы уничтожала набранный текст. Теперь: Enter + автосохранение
  через 1,5 с + `sendBeacon` при закрытии вкладки, отметка ставится после
  успешного ответа, черновики переживают перерисовку.
* **Сбор и парсер не блокировали друг друга** и работали в одном Chrome.
  Добавлен замок на браузерную сессию. Проверено: второй запуск отклоняется.
* **Ошибки сервера уходили в браузер как HTML** → «Ошибка сети: SyntaxError».
  Все обработчики обёрнуты, ответ всегда JSON.
* **401 отдавал текст, а клиенты ждали JSON** → непонятная ошибка вместо «нужен
  вход».
* **Полоса прогресса сбора была невидимой** — у обёртки не было CSS-правила.
* Удалён мёртвый код: `#warnbar`, неиспользуемые `verifyLabels`, теневые
  переменные, две системы прогресса, дублирующиеся форматтеры.

### Фазы 1–2: интерфейс

* **Вкладки**: Продавцы · Отсеянные · Сбор (старый парсер категорий убран из
  интерфейса, код оставлен).
* **Пагинация**: жёсткий лимит 300 строк заменён на серверную постраничную
  навигацию с честным «1–50 из 252».
* **Сортировка** по восьми столбцам с индикатором направления.
* **Фильтры**: статус, провинция (27 значений), уровень достоверности.
* **Честный подсчёт**: `count_sellers` теперь учитывает все фильтры — раньше
  «N из M» врало. Условия собираются одним построителем для списка и подсчёта.
* **Экспорт CSV из интерфейса** с учётом активных фильтров (раньше кнопка
  выгружала таблицу старого парсера).
* **Карточка продавца**: все поля, юрлицо и адрес, **причины, по которым
  считается китайским** (раньше не показывались нигде), товар-источник,
  история отправок, ссылки на Ozon.
* **Кнопка «Кому писать сегодня»** — подтверждённые, кому не писали, по оценке.
* **Массовые действия** — смена статуса и возврат в очередь для выделенных.
* **Пометка «+N витрин»** — у одной компании бывает несколько магазинов.
* **Вкладка «Отсеянные»** — 22 записи с причинами отсева и удалением.
* **Шапка**: подтверждённых, отсеянных, провинций, дата сбора, дата бэкапа.
* **Клавиатура**: Enter — сохранить заметку, Esc — закрыть карточку, `/` — поиск.
* Сводка и лог обновляются по SSE без перезагрузки страницы.

### Замечено при работе

* Тестирование удаления на живых данных снесло 3 записи из отсеянных — они
  восстановлены из снимка базы. Урок: разрушительные проверки надо делать на
  копии базы, а не на рабочей.

## v0.9 — 25.09.2026 — Панель рассылки, Фаза 3

Перед вшиванием автоотправки нашлось **шесть багов**, из-за которых включать её было
нельзя. Они важнее самого интерфейса, поэтому сначала они.

### Исправлено

* **Отправка смотрела в чужую базу.** `run_outreach.py` работал с
  `outreach_data/queue.sqlite3`, который создавался только командой `import`, а
  данные жили в `data/sellers.sqlite3`. Отправлять было физически некому.
  Теперь CLI и панель работают с общей базой; команда `import` убрана как
  ненужная.
* **Предпросмотр портил данные.** `claim_next` списывал попытку и ставил статус
  «пропущен» ДО проверки `dry_run` — один клик «предпросмотр» сжигал продавца из
  очереди. Теперь предпросмотр только показывает первого кандидата, ничего не
  меняя. Проверено: попытки 0, статусы не изменены.
* **Отправщик убивал общий Chrome.** `driver.quit()` вместо `manager.close()` —
  окно браузера исчезало, в отличие от парсеров. Теперь закрывается только своя
  вкладка.
* **Отправщик не переключал вкладку.** При параллельном сборе или парсинге
  активной могла оказаться чужая вкладка, и текст ушёл бы не на ту страницу —
  тот же класс бага, что был у парсеров с перепутанными данными. Добавлен фокус
  вкладки перед каждым действием.
* **Дневной лимит считался неверно.** По `updated_at`, который меняется от любой
  правки: отметка «ответил» или заметка съедали лимит и сокращали отправки.
  Плюс граница суток была по UTC, а не по местному времени. Добавлена колонка
  `sent_at`, лимит считается по фактическим отправкам за местные сутки.
  Проверено: ручная отметка статуса больше не влияет на лимит.
* **Повтор после ошибки не работал.** Статус «ошибка» был тупиковым: ничего не

## v1.0 — 25.09.2026 — Чат с продавцом: реальные селекторы вместо догадок

Схема отправки снята с живой страницы в залогиненной сессии. До этого
селекторы чата были неизвестны, и отправка была заблокирована.

### Выяснено

* **Чат открывается со страницы магазина.** На `/seller/{id}/` есть ровно одна
  кнопка «Написать», она ведёт в чат. Товар больше не нужен: чат привязан к
  продавцу, а не к товару.
* **Прямая ссылка на чат требует подписи.** Вид
  `/my/chat/?...&url_sign=<токен>&user_id=<seller_id>` — токен генерируется на
  клиенте при нажатии. Без него Ozon срезает параметры и открывает главную.
  Поэтому воспроизводим нажатие кнопки.
* **Классы Ozon обфусцированы и содержат хеш сборки** (`om_17text--SRiT5`).
  Привязка к ним сломалась бы на первом обновлении фронтенда, поэтому
  селекторы структурные.
* **Кнопка отправки опознаётся по поведению:** у неё нет ни текста, ни
  `aria-label`, ни `testid`, но она заблокирована при пустом поле и
  разблокируется после ввода.
* **Признак входа сменился:** `[data-widget^=profileMenu]` больше ничего не
  находит, а у залогиненного есть ссылка `a[href="/my/main"]`.

### Изменено

* `outreach_data/selectors.json` заполнен реальными селекторами.
* Отправка теперь идёт по `seller_id`, а не по ссылке на товар. Требование
  ссылки снято: **очередь выросла с 251 до 565 продавцов**.
* `confirm_sent` считает признаком успеха очистку поля ввода — Ozon не отдаёт
  квитанцию, и «нажали кнопку» не доказательство.
* `inspect_chat` переведён на страницу магазина и предлагает проверенные
  структурные селекторы.

### Готовность

Чек-лист отправки: разметка чата — **настроена**, очередь — **565 готовы**,
осталось только написать текст сообщения.

## v1.1 — 25.09.2026 — Авторизация и тестовый прогон

### Добавлено

* **`run_outreach.py login`** — открывает Chrome с профилем парсера для входа в
  Ozon и ждёт, пока вход действительно произойдёт. Профиль парсера отдельный:
  сессия из обычного браузера в него не переносится, поэтому вход делается один
  раз именно в этом окне.
* **Ограничение прогона** — «отправить не больше N сообщений и остановиться».
  Есть в CLI (`--limit`) и в дашборде (поле во вкладке «Рассылка»). Нужно для
  проверки на нескольких продавцах, не дожидаясь дневного лимита.

### Исправлено

* **Предпросмотр вставал в бесконечное ожидание вне рабочего окна.** Рабочее
  окно (10:00–19:00) применялось и к предпросмотру, хотя тот ничего не
  отправляет: вечером он уходил в цикл «ждём 600 секунд» до утра. Теперь окно
  ограничивает только реальную отправку. Проверено: в 21:30 предпросмотр
  разрешён, реальная отправка — нет.
