# Lead Intelligence — оценка и приоритизация продавцов (v1.17, раздел 11 ТЗ)

Система ищет продавцов с высокой вероятностью интереса, но НЕ дублирует
существующие подсистемы: скоринг расширяет `src/outreach/scoring.py`,
классификация ответов — существующие категории `src/crm/classify.py`/store,
A/B — `TemplatePool` + журнал, воронка — новый журнал поверх существующих
статусов и стадий.

## 1. Два направления оценки (§11.2)

**Commercial Score (0–100)** — коммерческий потенциал. Собран из ТЕХ ЖЕ
компонентов, что и базовый score (лог-шкала объёмов, срок, рейтинг), плюс
ассортимент, целевые категории и полнота/свежесть данных:

| Компонент   | Нормировка                    | Вес по умолчанию |
|-------------|-------------------------------|------------------|
| orders      | log10(n+1) / log10(1M+1)      | 0.25             |
| reviews     | log10(n+1) / log10(100k+1)    | 0.15             |
| tenure      | месяцы / 36 (макс 1)          | 0.15             |
| rating      | рейтинг / 5                   | 0.20             |
| assortment  | товаров / 500 (макс 1)        | 0.10             |
| category    | ниша ∈ целевым (0/1)          | 0.15             |

Итог умножается на **полноту данных** (доля заполненных полей) и **свежесть**
метрик (старше 14 дней — штраф 15%). Пустота данных — не «плохой продавец»,
а низкая уверенность: она занижает балл и прямо объясняется словами.

**Engagement Score (0–100)** — вовлечённость по фактам коммуникаций из
журнала: база 50 + вес каждой категории ответа (interested +30, positive +25,
needs_info +15, negotiation +25, question +10, neutral +5, negative/refusal
−40). Уровень уверенности: <2 ответа — «низкая», <5 — «средняя», дальше
«высокая». Это предварительная оценка, а НЕ вероятность согласия — менеджер
видит уровень уверенности рядом с числом.

**Итоговый приоритет** = `priority_mix` × Commercial + (1−mix) × Engagement
(по умолчанию 0.7/0.3).

## 2. Градация лидов (§11.3)

A ≥ 75, B ≥ 60, C ≥ 40, иначе D; **Unqualified** — продавец без подтверждения
(uscc/warehouse). Пороги, веса и целевые категории — в
`outreach_data/lead_config.json` (файл можно не создавать). Ручная смена
категории фиксирует причину: `POST /api/seller/grade {seller_id, grade,
reason}` — источник становится `manual`, авто-пересчёт ручную категорию не
затирает.

Объяснимость: `score_lead()` возвращает компоненты и причины словами —
каждый пересчёт можно показать менеджеру.

## 3. Единая история и мультиаккаунт (§11.5)

**Одна карточка продавца — одна глобальная история**, у сообщений —
аккаунт отправителя:

* таблица `sender_accounts` (account_id, label, last_used_at);
* в `messages` добавлены `sender_account_id`, `campaign_id`,
  `experiment_id`, `platform_message_id` (миграция на живой базе);
* аккаунт задаётся в настройках отправки (`sender_account_id`), регистрируется
  автоматически при первом использовании.

**Защита от дублей между аккаунтами:** перед отправкой каждого сообщения
проверяется ОБЩАЯ история продавца (`store.prior_contact`), а не только
локальная история аккаунта. Статуса продавца недостаточно — его мог сбросить
оператор, журнал же не переписывается никогда. Политика повторов — в
настройках отправки:

* `repeat_contact_policy = "never"` (по умолчанию): второй аккаунт НЕ напишет
  тому, кому уже писал первый;
* `"after_days"` + `repeat_after_days = N`: фоллоу-ап разрешён только спустя
  N дней после последней отправки.

Отказ от рассылки (opt-out) — глобальный: действует для всех аккаунтов и
кампаний немедленно.

## 4. Классификация ответов (§11.6)

Внутренние категории classify.py отображаются в публичные термины:
Positive (positive/interested), Question (needs_info/question), Negotiation,
Neutral, Refusal (negative), Opt-out (optout), Unknown (other). Исходный текст
ответа хранится ЦЕЛИКОМ и никогда не заменяется классификацией. Неуверенные
случаи (other/Unknown) идут менеджеру через существующий handover.

## 5. Воронка (§11.7)

Журнал `lead_events` (аддитивный, как seller_categories):
Imported → Qualified → Prioritized → Contacted → Replied → Interested →
Negotiation → Deal / Lost / Opted Out. События пишут существующие действия:
отправка → contacted, ответ → replied/interested, opt-out → opted_out,
стадия оператора → negotiation/deal/lost. **Автоматический путь в Deal
запрещён кодом** — сделку фиксирует только оператор через `/api/seller/stage`
(положительный ответ открывает лишь «interested»). Панель считает
достижимость этапов кумулятивно.

## 6. Эксперименты (§11.4)

* `POST /api/experiments/create {name, criteria:{min_score,max_score,limit},
  variants:["msg01","msg02"]}` — критерии и варианты сохраняются в
  `experiment_versions` (история изменений), назначение варианта —
  детерминированный хэш `sha256(seller_id:experiment_id)` → один и тот же
  продавец всегда в одной группе (воспроизводимость);
* отправка учитывает назначение: продавцу в эксперименте уходит РОВНО текст
  назначенного варианта (главнее ротации и A/B), `experiment_id` пишется в
  журнал сообщения;
* `GET /api/experiments?id=N` — отчёт по вариантам: назначено/отправлено/
  ответило/доля ответов + **baseline группы** (средние score, заказы,
  рейтинг) + честный уровень уверенности («мало данных» при <30 отправок).
  Сравнивать варианты нужно с поправкой на baseline: без неё «успех» шаблона
  может быть заслугой более качественной группы;
* `POST /api/experiments/finish {id}` — завершить.

## 7. Аналитическая панель (§11.9)

Страница **`/leads`** (за той же авторизацией) + эндпоинты:

* `GET /api/analytics` — база (всего/квалифицировано/градации/регионы/ниши),
  эффективность коммуникаций (отправлено, ответы, положительные, отказы,
  переговоры, сделки), воронка (достижимость этапов) и последние переходы;
* `GET /api/leads/top` — топ очереди с категориями и задачами;
* `POST /api/leads/recompute` — пересчёт скоринга (после правки
  lead_config.json); карточка продавца пересчитывается также при ответе;
* `POST /api/seller/next-task {seller_id, task, when}` — следующая
  запланированная задача менеджера.

Все числа считаются SQL-агрегатами по фактам базы.

## 8. Автоматическая работа с приоритетами (§11.8)

Автономный режим (v1.16) выбирает продавцов из очереди, где порядок уже
учитывает: подтверждённость → ручной приоритет → score; глобальная история
исключает повторные контакты (см. §3), глобальный opt-out исключает навсегда,
риск-стоп останавливает всё при ограничении платформы. Стратегия настройки —
без кода: `outreach_data/lead_config.json` (веса, пороги, целевые ниши) и
`outreach_data/sender.json` (интервалы, лимиты, политика повторов).
