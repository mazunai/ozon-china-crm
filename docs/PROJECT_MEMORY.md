## 27.09.2026 — сессия 7: закрытие аудита (39 находок) и типографика

### Как проводился аудит

/workflow: 6 параллельных сабагентов (4 аудита кода с цитатами path:line +
2 веб-исследования) → независимые конфирматоры для high-находок (нашедший не
подтверждает сам) → синтез-аналитик → холодная вычитка. Итог: 39 находок
(6 high, 16 medium, 17 low), 0 неподтверждённых. Отчёт — docs/DEEP_AUDIT.md.

### Главные находки и почему они возникли

1. **Логин писал два ответа в одно соединение** (второй `return
   self._send_json` после 303) — это и был корень BrokenPipe-спама, который я
   в v1.13.1 погасил только на стороне записи. Урок: гасить симптом — не чинить
   причину; следующий аудит это вскрыл за минуту.
2. **Утечка BROWSER_LOCK в Service.start** — замок брался до опасного участка
   без finally; воспроизведено вживую («Браузер занят» навсегда после одного
   неудачного /api/start).
3. **Взаимная невидимость фоновых процессов**: ночной сбор не видел ретро-проход
   и воркер, рассылка/inbox/ответы не видели ночной сбор — добавлены
   симметричные проверки в обе стороны.
4. **UPDATE add_sellers затирал непустые метрики пустыми** — в живой базе
   нашлось 21 подтверждённых с обнулённым uscc. Защита пустотой + verified_by
   только вверх (легаси-путь понизить больше не может).
5. **inbox открывал чат до сохранения** — Ozon помечает чат прочитанным, и
   падение save теряло ответ навсегда. Теперь превью сохраняется ДО открытия,
   полный текст дотягивается update_reply_text; каждый пузырь — отдельная
   строка журнала.
6. **restore() в backup_db копировал WAL-файл** — safety-копия пуста/битая;
   теперь pid-проверка дашборда + Connection.backup. Офсайт: messages.csv в
   --push, parser-backup.service получил --push, launchd на Mac (12:00 daily).

### Заделы, которые стоит знать наследникам

* Проверки занятости браузера теперь СИММЕТРИЧНЫ: каждая стартующая задача
  (ночной, ретро, рассылка, воркер, legacy, inbox, ответ) проверяет всех
  остальных. Новую фоновую задачу — по этому же шаблону.
* add_sellers защищён от пустоты: новые поля с «пустым» значением добавляйте
  в CASE-паттерн, иначе транспортный сбой обнулит данные.
* HTTP-слой дашборда теперь тестируем: тест поднимает сервер на эфемерном
  порту с временной базой (test_dashboard_http.py) — добавляйте эндпоинт-кейсы
  туда же.
* Типографика стат-строк: .fb-count с white-space:nowrap и min-width — счётчик
  не переносится; .fb-fill с min-width 4px всегда виден.

### Задача из promt.md

Градировать продавцов по категориям товаров — для статистики и понимания,
какая ниша активнее идёт на контакт. Жёсткая рамка: сначала аудит, без
мутаций существующих данных.

### Аудит (что выяснено до строчки кода)

* Карточка товара НЕ содержит поля «category» (первый щуп дал 0 совпадений) —
  категория живёт в виджете `breadCrumbs` (хлебные крошки), найденном вторым
  щупом по признаку «bread».
* Список `/category/`-ссылок в JSON — глобальное меню сайта (одинаково на
  карточке и у продавца), сигналом не является.
* Последняя крошка — бренд (двухсегментная ссылка); отфильтровывается.
* База готова: 4667/4679 подтверждённых продавцов имеют товар в кэше —
  ретроактивно покрыть можно почти всех, по одной карточке на продавца.

### Решения

* Категории — ЖУРНАЛ замеров (`seller_categories`, только INSERT): актуальная
  запись по MAX(id), история не переписывается. Это и есть исполнение рамки
  «не потерять правду»: замер — новое измерение, а не правка продавца.
* В основном сборе категория снимается с уже открытой карточки: +0 запросов.
* Ретро-проход — отдельным скриптом с lock/стоп-краном, уважает ночной сбор,
  обычный сбор и рассылку (браузер общий), сам продолжается после сбоев.

## 26.09.2026 — сессия 5: пустые «Отсеянные» и настройки сборов

### Жалобы пользователя и что под ними оказалось

1. **«В отсеянных вообще ничего нет, данные пропали»** — данные на месте
   (511 записей, шапка их считала), вкладку убивала JS-ошибка: v1.11.0
   добавила в `params()` чтение `t.categories.length`, но поле `categories`
   появилось только у `T.sellers`, не у `T.rejected`. Клик по вкладке падал
   с TypeError до fetch, и вкладка выглядела пустой. Мораль: фильтр,
   добавленный для одной таблицы, ломает вторую, если состояние общее, а
   поля — нет. Починено добавлением поля И защитой в `params()`
   (`t.categories && t.categories.length`) — второе важнее первого.
2. **«Кнопка обновить в ночном сборе ничего не показывает»** — при
   незапущенном сборе `/api/night` отдавал нули, интерфейс рисовал прочерки.
   Теперь стейт-файл ночного сбора отдаёт `last_result`/`failures`, и
   «Обновить» показывает: «не идёт · последний прогресс … · продолжит со
   страницы N · прошлый чанк упал с ошибкой».
3. **«Хочу менять ссылку и чтобы сохранялось»** — ночной сбор ходил только
   по дефолтному разделу (`--url` существовал в CLI, но дашборд его не
   передавал), а все параметры задавались заново каждый раз. Введены
   сохраняемые настройки обоих сборов.

### Решения

* **Настройки — в `data/harvest_settings.json`**, а не в config.txt и не в
  localStorage: файл вне git, деплой `data/` не трогает — на каждой машине
  (Mac и VM) свои настройки, переживают перезапуск дашборда. Разделы
  `harvest` и `night` независимы: ночью один раздел, днём другой.
* **Валидация до запуска**: `save_harvest_settings` проверяет ЧЧ:ММ, домен
  ozon.ru и диапазоны; старт ночного сначала сохраняет настройки и только
  потом запускает — кривое «работать до» не запускает сбор, который упадёт
  на первом чанке. Запуск обычного сбора тоже запоминает, что запустили
  (ошибка сохранения не срывает уже запущенный сбор).
* **Диагностика JS в этом дашборде**: скрипт в IIFE, глобалей не видно;
  `performance.getEntriesByType("resource")` показывает, какие /api/ запросы
  реально ушли, а ловушка `window.addEventListener('error')` установленная
  БЕЗ перезагрузки ловит ошибку клика — этой парой инструментов баг
  «Отсеянных» найден за минуты.

### Проверки

`test/test_harvest_settings.py` — 14 кейсов: дефолты, round-trip,
отклонение кривых значений, срезание диапазонов, частичное сохранение,
статус ночи из стейт-файла. Полный набор зелёный (23+14+33+14+30+23+14+7+9).
В браузере проверено: вкладка «Отсеянные» (50 строк с причинами отсева),
автозаполнение полей из настроек, сохранение и перезагрузка, тост ошибки
валидации, карточка продавца с историей переписки, живость в таблице.

## 26.09.2026 — сессия 4: живость продавца (отвечает ли он на отзывы)

### Задача от пользователя

Новый сигнал для приоритизации рассылки: «живость» продавца по отзывам —
отвечает ли он покупателям. Бриф требовал: сначала проба API с точными
именами полей (не угадывать), аддитивная миграция, сглаживание Лапласа,
сэмпл на уже открытой карточке (+1 запрос), UI: колонка с сортировкой,
блок на «Обзоре», фильтр молчуны/отвечающие.

### Что дала проба API (8 пробников на VM, главные сюрпризы)

1. **В карточке отзывов нет вообще** — только счётчик `webReviewProductScore`
   с адресом страницы отзывов и `reviewsCount`. Бриф предполагал найти отзывы
   прямо в карточке; пришлось добавить ещё один запрос — страницу отзывов.
   Итого сэмпл стоит +1 запрос к карточке (а не 0) — в рамках заложенного.
2. **`comments.list` в общей выдаче всегда пуст.** Тело комментариев приходит
   только по якорной ссылке `?ruuid={uuid отзыва}` и только для якорного
   отзыва. Значит «посчитать ответы по всем 30 отзывам бесплатно» нельзя.
   Решение: якорим максимум 2 отзыва с комментариями на карточку (обычно их
   0–3 из 30), непроверенные — выпадают из сэмпла. Отзыв без комментариев
   разрешён достоверно: ответ продавца сам был бы комментарием.
3. **`isUserComment` не различает продавца и покупателя** — у обоих `False`.
   Настоящий признак — `author.clientOfficial.id != "0"` (у магазина там его
   seller_id, `partnerType: 1`, `brandUri`). Найдено сравнением живого ответа
   OUYA01 и живого комментария покупательницы; кейс закреплён в тесте.
4. **totalCount>0 ≠ ответ продавца**: в комментариях пишут и покупатели —
   наивный «счётчик обсуждений» завышал бы живость. Поэтому только якорение.
5. Страница `/seller/{id}/reviews/` отдаёт оболочку без списка отзывов —
   «все отзывы продавца одним запросом» не получилось (помечено в AGENTS.md).

### Решения

* **Кумулятивно по продавцу, не по товару**: один продавец держит много
  витрин-товаров, отзывы на них — один и тот же продавец. Сэмплы с разных
  карточек и прогонов складываются (`record_review_sample`), у сэмпла есть
  свежесть `reviews_checked_at`.
* **Честность важнее полноты**: непроверенный отзыв не считается молчуном —
  лучше меньший знаменатель, чем завышенная «молчаливость» (см. п. 2).
* **Один сэмпл на продавца за проход**: карточек у продавца много, отзывы
  на них пересекаются — дедуп по `seller_id` за проход (`_vitality_sampled`).
* **Сглаживание Лапласа** `(r+1)/(s+2)` и пороги 0.5/0.25 вынесены в чистый
  модуль `vitality.py`; те же пороги выражены алгеброй в SQL для фильтра и
  сортировки, тест сверяет обе записи на сетке 40×40 — если кто-то поправит
  порог в одном месте и забудет в другом, тест упадёт.
* **Сэмпл не роняет сбор**: `sample_from_card` гасит все исключения.
* Сортировка по живости ставит «мало данных» в конец списка (CASE … ELSE -1),
  а не в середину по дефолтным 0.5.

### Проверки

23 кейса `test/test_vitality.py` (формула, границы категорий, SQL-эквиваленты,
опознание ответа продавца на живых примерах, учёт сэмпла). Существующие
наборы зелёные: 33 + 14 + 23 + 14 + 30 + 7. Миграция обкатана на копии живой
базы (3217 продавцов): колонки добавлены, счётчики копятся (30+30 → 60),
фильтры и сортировка не падают на пустых значениях.

### Инфраструктурная заметка

VM `yc-user@51.250.84.76` (`tools/deploy_vm.sh`) жива и синхронна с локальным
деревом; раздел 5.1 про `ubuntu@130.193.51.137` устарел — та машина не
отвечает по SSH. При деплое не забыть, что rsync в `deploy_vm.sh` гонит ВСЁ
дерево с `--delete` — по правилам этой работы деплоить поимённо и сверять
sha256.

## 26.09.2026 — сессия 3: сохранение результатов коммуникации

### Задача от пользователя

Перед массовой рассылкой нужна гарантия, что результат каждой коммуникации
сохраняется: кому писали, когда, что отправили, что ответил (ПОЛНЫЙ текст и
дата), категория ответа, статус. Отдельный список заинтересованных и
возможность передать продавца менеджеру. Явные ограничения: парсер не
переписывать, отдельной системы не создавать.

### Что было (неожиданно много)

В базе уже жили журнал `messages` (result='sent'/'received'), статусы,
стадии сделки и авто-пометка «ответил» из чатов. Пробелы были ровно те,
что назвал пользователь:

1. Входящие сохранялись **превью из списка чатов** с вклеенным префиксом
   «[входящее 26.09 02:00]» — полный текст ответа терялся.
2. Категорий ответов не существовало вообще.
3. Не было отметки «передан менеджеру» и отчётов по категориям.

### Решения

* **Текст ответа — главный артефакт.** В `messages` пишется целиком, без
  префиксов; дата получения — в `sent_at` строки, а не в тексте. Префиксы
  старых записей вычищены через `recategorize` (обратимо: он же пересчитывает
  категории по обновлённым правилам).
* **Полный текст добывается из страницы чата** (deeplink из списка чатов
  подставляется в композер-API). Разметку снять не удалось — нужна живая
  сессия, поэтому извлечение либеральное и с fallback на превью. Помечено в
  AGENTS.md как непроверенное — проверить при первом реальном ответе.
* **Категории — ключевыми словами** (`classify.py`), а не моделью: на десятках
  ответов правила прозрачны и правятся, а `recategorize` пересчитывает историю,
  потому что тексты хранятся целиком. «НЕ ОТВЕТИЛ» не хранится в базе — это
  отсутствие входящего, его выводят отчёты (иначе пришлось бы синхронизировать
  производное состояние).
* **Заинтересованные без копий**: `positive` + `interested` + `needs_info`
  фильтруются по `reply_category`. Отдельная «база заинтересованных» была бы
  вторым источником правды и рассинхронилась бы.
* **Передача менеджеру** — колонка `handed_to_manager_at` + автостадия
  «переговоры». Менеджер продолжает в том же журнале: ответы из дашборда и
  заметки уже писались в базу, новых механизмов не нужно.
* **Воронка переведена на журнал**: «Написали/Ответили» считаются по
  `messages`, а не по статусам — статус меняется руками и врёт.

### Проверки

27 новых кейсов (`test_communication.py`): классификатор (включая «не
интересно» → негатив), сохранение текста байт-в-байт, opted_out не
переворачивается ответом, списки, миграция легаси-базы, разбор вложенных
JSON-строк композера. Существующие наборы зелёные (test_gui падал по tkinter
и до правок). Миграция живой базы (3217 продавцов) прошла, перед ней сделан
снимок `tools/backup_db.py`.

### Проверка на живом чате (в тот же день)

Дождались применения на реальном ответе (YM Store, «Дорогой друг, чем я могу
тебе помочь?»). Выяснилось и проверено:

* композер-API страницы чата НЕ отдаёт сообщения — только оболочку аккаунта
  (они гоняются по WebSocket), а прямая ссылка без url_sign открывает главную;
  первый вариант извлечения из JSON остался бы бесполезным;
* рабочий путь — тот же, что у отправки: страница магазина → «Написать» →
  чтение DOM открытого чата. У сообщений есть атрибут `is-mine`; служебные
  сообщения «Ассистент Ozon» приходят с пустым is-mine и фильтруются по
  маркерам (`SYSTEM_REPLY_MARKERS`) — иначе подсказка системы стала бы
  «ответом продавца»;
* backfill по YM Store снял ровно тот же текст, что лежал в базе — превью
  не обрезало ответ. Длина как защита от мусора сработала и раньше: на
  первом (JSON-)варианте extraction возвращал надписи интерфейса, которые
  были короче превью и не перезаписали данные.

## 25.09.2026 — сессия 2: мини-CRM и починка ложных «китайцев»

### Задача от пользователя

Пользователь сообщил: прошлый прогон выдал ~135 продавцов с «100% вероятностью
Китай», но по ссылкам оказался российский ИП Маликов. Задача — сделать так,
чтобы в базу попадали **только подтверждённые** китайские продавцы, плюс
мини-CRM с заметками, статусами и сохранением между прогонами.

### Диагностика (до правок)

Разобрал сохранённые `output/*.json` и нашёл три разных проблемы, а не одну:

1. **137 записей о товарах, но всего 27 уникальных продавцов** — «135 продавцов»
   было иллюзией: одно юрлицо давало много строк товаров.
2. **Одна китайская компания (`Fuzhou Tegeile Trading Co., Ltd`) оказалась
   приписана пяти разным витринам**, включая «Яндекс Фабрику», OSRAM и Ralph
   Lauren. Три китайские фирмы на 15 магазинов — так не бывает.
3. **В поле компании попадал текст интерфейса**: «Фото и видео покупателей»,
   «Товар закончился». Классификатор судил о стране по этому мусору.

Вывод: дело не в пороге уверенности, а в **перепутанных данных**. Гипотеза о
нестрогой регулярке USCC подтвердилась лишь частично — USCC в данных были
настоящие, а вот привязка «товар → продавец» ломалась.

### Корневая причина

**Гонка на общей вкладке Chrome.** `SeleniumManager` подключается к запущенному
Chrome через порт отладки (`debuggerAddress`), а при таком подключении
`driver.get()` управляет текущей активной вкладкой. Все воркеры работали в
одной вкладке и перезаписывали друг другу страницу: воркер A ждал JSON продавца
AAA, воркер B уводил вкладку на BBB, воркер A читал чужие реквизиты.

Именно поэтому российскому ИП достались реквизиты китайской фирмы, а в поле
компании попадал текст чужой страницы.

### Что сделано

**1. Починена гонка** (`src/utils/selenium_manager.py`)
Каждый воркер открывает свою вкладку (`_open_own_tab`) и делает её активной
перед каждой операцией (`_focus_tab`); закрывает тоже только свою. Отдельно
проверено, что `camoufox_manager.py` этой болезни не имеет — там отдельная
страница на воркера.

**2. Ужесточён классификатор** (`src/parsers/chinese_filter.py`)
* Убрана нестрогая регулярка `\b[0-9A-Z]{18}\b` — она ловила служебные токены
  Ozon и давала «китайский код» российским ИП. Остался строгий формат
  `9[123]\d{6}[0-9A-Z]{10}`.
* USCC, иероглифы и «Китай» больше не ищутся по всему сырому JSON — только в
  полях продавца: названии, реквизитах, ИНН.
* Подтверждённая российская регистрация (ОГРН/ОГРНИП/ИНН) перебивается только
  строгим USCC. Российский продавец, торгующий китайским товаром, остаётся
  российским — это и есть то, что просил пользователь.
* Добавлен разбор блока реквизитов (`extract_seller_registration`) и вывод
  провинции из кода региона USCC (`province_from_uscc`).

**3. `seller_parser` берёт реквизиты правильно**
Раньше «лучший textBlock» выбирался внутренним скорингом, и туда попадал текст
интерфейса. Теперь ищется блок, у которого последняя строка — регистрационный
номер (18-значный USCC или 15-значный ОГРНИП). Проверено на живых модалках:
три китайских продавца опознаются с провинциями, российский ИП — как `ogrnip`,
четыре мусорных текста отбраковываются.

**4. Создано хранилище** (`src/crm/store.py`)
Одна SQLite на проект: `data/sellers.sqlite3`. Это и очередь рассылки, и
CRM. Дашборд читает базу, а не память. Есть миграция: старая база очереди
получает недостающие колонки через `ALTER TABLE`, история отправок сохраняется
(проверено — статус `sent` не теряется).

Ключевое решение: **уровень достоверности** (`verified_by`). У продавца в базе
хранится, чем подтверждена страна: `uscc` (абсолютно), `warehouse` (склад в
Китае), `heuristic` (эвристики по названию). В дашборде и в рассылке по
умолчанию участвуют только первые два — эвристики, которые и давали ложные
плюсы, отсечены от выдачи, но не удалены.

**5. Написан харвестер** (`src/crm/harvest.py`)
Обход раздела «Товары из Китая»: страницы → товары → продавцы → реквизиты →
база. Главная защита — выбор правильного грида: берётся только тот, у которого
`params` строго `"{}"`; грид с `"title"` в params отбрасывается как
рекомендации (там российские товары).

**6. Дашборд стал CRM** (`dashboard/server.py`, `web/index.html`)
* Вкладка «Китайские продавцы»: USCC, провинция, метрики, оценка, статус,
  заметка, ссылка на профиль.
* Авторизация HTTP Basic, пароль в `.env`. Дашборд публикуется наружу через
  SSH-туннель, без пароля там были бы открыты бизнес-данные.
* Больше **не обнуляет** список при старте нового парса.
* По завершении парса автоматически сохраняет продавцов в базу.

## 25.09.2026 — сессия 1: разведка Ozon и отправщик

### Что выяснено про Ozon (всё проверено на живом сайте)

* Ozon отдаёт `403` с `ozon-antibot: 1` обычным HTTP-клиентам, поэтому все
  запросы идут через браузер.
* `webDelivery` в ответе карточки всегда пустой — состояние грузится отдельным
  POST с `asyncData` из `layout`. Без него — 400. Контракт вытащен из их же
  `main.js`.
* Раздел `/highlight/tovary-iz-kitaya-935133/` — «Товары из Китая»; рядом есть
  отдельные разделы для Турции и категорий «из-за рубежа».
* `from_global=true` — флаг контекста, не фильтр (проверено сравнением выдачи).
* `country`/`countryCode`/`countryId` — страна покупателя, не продавца.

### Что сделано

Модуль рассылки (`src/outreach/`): оценка продавцов с логарифмическим сжатием,
SQLite-очередь с дедупликацией и стоп-листом, шаблоны с русскими склонениями,
отправщик с интервалом, дневным лимитом, рабочим окном и стоп-краном,
инспектор разметки чата.

**Решение по этике:** реализованы ограничители и стоп-лист, но не делается
обход детекции (подмена отпечатков, мультиаккаунт для обхода лимитов).
Причина не в морали, а в том, что это инструмент против чужой системы защиты;
обычная автоматизация с паузами — пожалуйста.

### Открытый вопрос

Пользователь просил автопостинг сообщений. Реализован низкочастотный вариант
(по умолчанию 1 сообщение в час, лимит 12 в сутки, рабочее окно) с
ограничителями, но **без** бесконечной автоматической рассылки: это спам,
нарушение правил Ozon и риск для аккаунта. Отправка ждёт залогиненного
аккаунта, чтобы протестировать на одном продавце.
